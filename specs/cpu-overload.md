# SPEC — Agent: CPU 과부하 상태 판정

## 목표

Agent가 실행 중 직접 측정한 CPU 사용률 이력(메모리 상의 최근 측정값
목록)을 바탕으로, "CPU 90% 이상이 5초 이상 끊기지 않고 지속됐는지"를
실제 타임스탬프로 판정해 **데이터 부족 / 정상 / CPU 과부하 후보** 세
상태 중 하나로 구분하고, 그 결과를 Agent 콘솔에서 확인할 수 있게 한다.

이 기능은 상태만 구분한다. 어떤 프로그램이 원인인지는 판단하지 않는다
(관련 프로세스 분석은 다음 슬라이스).

## 이번 슬라이스 완료 조건

1. CPU 과부하 판정 순수 함수를 TDD로 구현한다 (`agent/cpu_agent.py`).
2. `agent/main.py`가 실제 측정값의 최근 이력을 메모리에 유지한다.
3. 매 실제 CPU 측정 성공 직후 판정 함수를 호출한다.
4. 실제 Agent 콘솔에서 현재 상태가 `데이터 부족` / `정상` /
   `CPU 과부하 후보` 중 하나로 표시된다.
5. 기존 CPU 측정 및 production 업로드 기능(연결, 측정, 업로드 성공/실패
   로그)은 그대로 유지한다 — 이번 슬라이스로 인해 깨지지 않는다.

## 입력 데이터

- `history`: 시간 순으로 정렬된 측정값 목록. 각 항목
  `{cpuPercent: number, measuredAt: ISO8601 문자열}`.
- Agent가 실제로 측정에 성공할 때마다(=업로드를 시도하는 그 값) 이
  목록 끝에 추가한다. 측정 실패로 건너뛴 주기는 목록에 추가하지 않는다
  (측정하지 않은 값을 채워 넣지 않는다).
- 판정 함수는 항목 간 간격이 항상 일정하다고 가정하지 않는다.
  `measuredAt` 간의 실제 시간 차이만으로 지속 시간을 계산한다.

## 상수 (경계조건까지 고정값으로 명시)

| 상수 | 값 | 의미 / 경계 |
|---|---|---|
| `CPU_HIGH_THRESHOLD_PERCENT` | `90.0` | `cpuPercent >= 90.0`이면 "높음". `89.9...`는 "높음 아님". |
| `MIN_SUSTAINED_SECONDS` | `5.0` | 연속 구간의 (끝 시각 − 시작 시각) `>= 5.0`초면 "지속됨". `4.999...`초는 미달. |
| `MAX_SAMPLE_GAP_SECONDS` | `4.0` | 현재 `MEASURE_INTERVAL_SECONDS(2.0초)`의 2배. 연속된 두 측정 시각 차이가 `<= 4.0`초면 "같은 구간(연속)"으로 본다. `> 4.0`초면 "공백"으로 보고 그 지점에서 구간을 끊는다 (한 번의 측정 실패로 인한 건너뜀까지는 흡수하되, 그 이상은 흡수하지 않는다). |
| `HISTORY_WINDOW_SECONDS` | `60.0` | Agent가 메모리에 유지하는 최근 이력의 최대 폭. 판정 직전 `now - 60초`보다 오래된 항목은 버린다. 판정 로직 자체의 상수는 아니고 `main.py`의 이력 보관 정책이다. |

## 판정 로직

1. `history`에서 `cpuPercent`가 숫자가 아니거나 `measuredAt`이 파싱
   가능한 시각이 아닌 항목은 제외한다 (값을 추정해 채우지 않고, 그냥
   측정되지 않은 것처럼 취급한다).
2. 남은 항목이 **2개 미만**이면 → **데이터 부족** (지속 여부를 계산할
   기준점 자체가 부족함).
3. 남은 항목을 시간 순으로 훑으며 "연속 구간(run)"으로 묶는다. 연속
   구간은 다음을 모두 만족하는 연속된 항목들이다.
   - 각 항목의 `cpuPercent >= 90.0`.
   - 그 항목과 바로 이전 항목의 `measuredAt` 차이가
     `<= MAX_SAMPLE_GAP_SECONDS`.
   - 위 조건이 하나라도 깨지면 그 지점에서 구간이 끝나고, 조건을
     만족하는 항목부터 새 구간이 시작될 수 있다.
4. 각 연속 구간에 대해 `지속시간 = 구간 끝 measuredAt − 구간 시작
   measuredAt`을 계산한다. `지속시간 >= MIN_SUSTAINED_SECONDS`인 구간이
   하나라도 있으면 → **CPU 과부하 후보** (근거: 그 구간의 시작 시각,
   종료 시각, 지속시간(초), 구간 내 최고 `cpuPercent`).
5. 4번에서 과부하 후보가 확정되지 않았다면, 목록의 **마지막 항목**을
   확인한다.
   - 마지막 항목이 `cpuPercent >= 90.0`이면 (즉 지금 막 높은 구간이
     끝나지 않고 이어지고 있는 상태라면) 그 구간은 아직 끝났는지
     알 수 없고 5초를 채웠는지도 모른다 → **데이터 부족** (아직
     지속 여부를 판단하기에 관찰 시간이 충분하지 않음).
   - 마지막 항목이 `cpuPercent < 90.0`이면 → **정상**.

이 순서대로 실행하면 다음이 자연스럽게 성립한다.

- **한 번이라도 실제 타임스탬프로 5초 이상의 연속된 90%+ 구간이
  확인되면**, 그 이후 값이 낮아지더라도 이미 확인된 사실은 사라지지
  않으므로 계속 **CPU 과부하 후보**로 유지된다 (단, `main.py`가
  60초보다 오래된 항목을 버리면 그 오래된 근거도 함께 사라진다 —
  "걱정되는 것" 참고).
- 아직 5초를 채우지 못한 채 방금까지 계속 높았다면 **정상이라고
  단정하지 않고** 데이터 부족으로 보류한다.
- 이미 5초 미만에서 끝나고 그 뒤로 낮은 값이 관측됐다면, 그 구간은
  "지속되지 않은 것"으로 이미 결론이 난 것이므로 **정상**이다.

## 상태 정의 (요청하신 4가지로 정리)

| 상태 | 조건 |
|---|---|
| **데이터 부족** | 유효한 측정치가 2개 미만이거나, 마지막 측정치가 90% 이상인 채로 아직 5초 지속 여부를 확인할 만큼 시간이 지나지 않은 경우. |
| **정상** | 유효한 측정치가 2개 이상이고(충분한 관찰), 90%/5초 조건을 만족하는 구간이 없으며, 마지막 측정치가 90% 미만인 경우. |
| **CPU 과부하 후보** | 90% 이상인 값이 실제 타임스탬프 기준으로 5초 이상 끊기지 않고 지속된 구간이 하나라도 확인된 경우. |

## 샘플링 간격에 대한 명시 (임의 보간 금지)

Agent는 약 2초 간격(`MEASURE_INTERVAL_SECONDS`)으로 측정한다. 따라서
측정 시각이 0초, 2초, 4초, 6초처럼 찍힐 때, "5초 이상 지속"이
**최초로 확인되는 시점은 4번째 샘플(약 6초 시점)**이다.

- 0초, 2초, 4초 세 샘플만 있는 시점(경과 4초)에서는 아직 5초를
  채우지 못했으므로 **데이터 부족**이며, 없는 5초째 값을 보간하거나
  추정해서 "지속 5초"로 만들지 않는다.
- 6초 시점(0,2,4,6초 네 샘플, 모두 90% 이상)에 이르러서야 구간
  지속시간이 실제로 6초(`>= 5.0`)가 되어 **CPU 과부하 후보**로
  확정된다.

## 데이터 부족/누락 시 처리 요약

- **이력이 비어 있거나 1개뿐** → 데이터 부족.
- **관찰은 됐지만 아직 5초를 채우지 못한 진행 중인 고사용률 구간** →
  데이터 부족 (정상이라고도, 과부하 후보라고도 단정하지 않는다).
- **측정 실패 등으로 두 측정 사이 간격이 `MAX_SAMPLE_GAP_SECONDS`(4.0초)를
  초과** → 그 지점에서 구간을 끊는다. 끊긴 구간 이전 값들을 근거로
  이후까지 지속됐다고 단정하지 않는다.
- **필드가 없거나 타입이 잘못된 측정 항목** → 해당 항목만 제외
  (측정되지 않은 것처럼 취급), 나머지로 판정한다. 예외로 죽지 않는다.

## Agent 콘솔에서 보이는 결과 (완료 조건, 눈으로 확인)

매 측정 성공 주기마다 기존 출력(`CPU 사용률: NN.N%`, `업로드 성공`/
`업로드 실패: ...`)에 이어 상태 한 줄을 추가로 출력한다.

- `상태: 데이터 부족`
- `상태: 정상`
- `상태: CPU 과부하 후보 (98.2%, 07:00:00~07:00:06, 6.0초 지속)`

Agent를 실제로 실행해 CPU에 인위적으로 부하를 걸었을 때(예: 부하
테스트 도구 실행), 콘솔 상태가 `데이터 부족` → `정상`(또는 바로 고
사용률이면 `데이터 부족` 유지) → 부하 시작 후 약 5~6초 뒤
`CPU 과부하 후보`로 바뀌는 것을 눈으로 확인한다.
